### 6.4 Local Agent Security (Non-Negotiable)
- **Deny by Default:** The Local Agent has an immutable baseline deny policy.
- **Default-Protected Patterns:** `.env`, `.env.*`, `.ssh/**`, `id_rsa*`, `*.pem`, `*.key`, cloud credential files, secret stores, token files, OS/system-sensitive locations.
- **Capability Model:** Every capability has owner, scope, expiration, audit, revocation.
  - Example: `READ_WORKSPACE` scope `/Projects/MyProject/**`
  - Example: `WRITE_WORKSPACE` scope `/Projects/MyProject/src/**`
  - Example: `EXECUTE_COMMAND` with allowed-commands-only policy
  - Example: `NETWORK_ACCESS` with explicit allowlist
- **Capability Grant Requirements:** Explicit per-project allowlist. Configurable only through privileged security policy, never by arbitrary AI prompt.
- **Workspace sandbox** (chroot-like boundary)
- **Resource limits** (CPU, memory, disk, network)
- **Network policy** (block by default, whitelist explicit)
- **Command safety** (block `rm -rf /`, `dd`, `mkfs`, etc. unless explicitly overridden with extra confirmation)
- **Secret protection** (never read `.env`, `id_rsa`, `.aws/credentials`, `*.pem` unless explicitly authorized via secure capability grant)
- **Path traversal defense**
- **Symlink escape defense**
- **Full audit trail** (who, what, when, result)
- **Reversibility** (all changes logged for undo)

User must explicitly pair/authorize local agent via 6-digit code (10-min expiry, max 3 paired devices).

## SECTION 7: 24/7 AUTONOMOUS WORK SYSTEM

### 7.1 Definitive Architecture
IMPORTANT: 24/7 WORK DOES NOT MEAN A POWERED-OFF LAPTOP CAN EXECUTE LOCAL COMMANDS.

**A. CLOUD EXECUTION** — Runs when user is offline, asleep, away, laptop powered off.
Includes: research, planning, reports, memory processing, semantic indexing, scheduled reports, task orchestration, cloud-side code execution in approved isolated environments, notifications, payment reconciliation, report generation, autonomous analysis, background workers.

**B. LOCAL EXECUTION** — Requires Local Agent connected.
Includes: reading local files, editing local files, running local terminal commands, running localhost services, local tests, controlling local applications, local dev server operations, local Git operations where authorized.

**C. HYBRID TASK** — A task can move between cloud and local.
Example: "Research this library, update my local project, run tests and summarize."
Flow: CLOUD research → CLOUD plan → CLOUD prepare change → WAITING_FOR_LOCAL_AGENT → user turns laptop on → LOCAL AGENT CONNECTS → read files → edit files → run tests → verify → save artifacts → CLOUD summary → user notified.

"Unlimited messages" means:

It DOES NOT mean unlimited consumption of arbitrarily expensive model

- normal Cowork tasks continue
- standard file operations continue

COMPUTE GOVERNANCE MAY:

3. use capable models for standard requests;

5. limit excessive parallel execution;
6. limit abusive or pathological workloads;

IMPORTANT:

PREMIUM MODEL REQUEST
        ↓

"Unlimited" therefore means:

## SECTION 11: MEMORY & DNA SYSTEMS

### 11.1 Memory System (M&M)
Keep 5 types: Episodic, Semantic, Procedural, Project, Team.

Functions: extraction, search, semantic retrieval, edit, merge, correction, deletion, recovery, provenance, confidence, relationships, source inspection.

Every memory records: source, timestamp, project, type, confidence (0-100%), provenance, scope, contradiction state.

Memory retrieval fallback: vector search → keyword search → recent context.
If embedding service fails: store content, queue embedding job, continue operation.

Users can: inspect memories, create manual memory, correct memory, merge memory, delete, restore, search, inspect source, review confidence.
Never silently rewrite user-confirmed memories.

### 11.2 Memory Safety — Prevent Cross-Project Contamination
Every memory retrieval must consider: tenant_id, user_id, project_id, team_id, memory_type, scope, permission.

**Default:** CURRENT PROJECT ONLY.
**Optional:** SEARCH ALL AUTHORIZED PROJECTS (only when explicitly enabled).

**Memory Confidence Levels:**
- **VERIFIED:** Can be used automatically.
- **CONFIDENT:** Can normally be used automatically.
- **INFERRED:** Label internally and use carefully.
- **UNVERIFIED:** Do not inject automatically into critical actions.
- **CONTRADICTED:** Do not automatically use.

**Provenance:** Every memory links to: source conversation, source message, file, task, timestamp, project. UI: "Where did this memory come from?" → click → source.

**Wrong Memory Handling:** User flags "This is wrong." System must: lower confidence, mark contradiction, preserve provenance, prevent automatic reuse where necessary, create correction event. Never silently erase history.

### 11.3 Cold Start — Create Real Context Without Inventing Facts
On first project connection, inspect REAL project evidence: package.json, tsconfig.json, requirements.txt, pyproject.toml, docker-compose.yml, README.md, git metadata, directory structure.

Extract only facts that are actually observable.

**Memory Source Types (Mandatory Labeling):**
- **OBSERVED:** Fact directly found in files. Treat as direct fact.
- **USER_STATED:** Fact explicitly stated by user. Treat as direct fact.
- **AI_INFERRED:** Must remain labeled as inference.
- **RECOMMENDATION:** Suggestion, not fact.

Example:
- OBSERVED: "TypeScript is installed."
- OBSERVED: "Next.js appears in package.json."
- OBSERVED: "App Router directory detected."
- DO NOT STORE: "User prefers X" unless user actually demonstrated it.

### 11.4 Load DNA
DNA stores: decisions, unresolved work, next actions, important discoveries, project context, relevant files (up to 50), blockers, environment state, verification results.

DNA supports: auto-create on task completion, manual save, naming/description, cross-conversation restore, versioning with comparison, conflict detection + resolution, one-click load/resume, history timeline, sharing, export (JSONL), recovery from trash (30 days).

**Conflict Resolution:** Detect → preserve both → compare sources → resolve → create new resolved state. Never silently overwrite conflicting DNA.

### 11.5 Team Memory Survival — Versioned DNA with Branches/Merge
Shared DNA and memory require versioning.

Use: MAIN + BRANCH + MERGE.

Example:
- Alice: DNA branch A
- Bob: DNA branch B
- Main: stable project truth

**Merge Process:** Compare → detect conflicts → review → merge → new version.

**Permissions:**
- Viewer: read
- Editor: suggest/edit within permissions
- Owner/admin: merge/resolve

All versions remain recoverable. Never silently overwrite shared truth.
